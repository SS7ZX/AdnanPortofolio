02 / Case study

C-Pay, from cash problem to auditable flow.

The project matters less as a product claim than as a record of the decisions, constraints, and improvements I would make next.

The problem

Campus events needed a clearer payment trail.

Cash created reconciliation errors and made disputes difficult to resolve. C-Pay introduced a closed-loop wallet system for event check-in, merchant payment, and transaction history.

Architecture
CLIENT: React
  Event check-in | Wallet balance | Merchant terminal
                 |
API: Express and Node.js
  Auth middleware | Transaction service | Input validation
                 |
DATA: MongoDB
  Users and wallets | Transaction ledger | Event records
Key decisions

Keep high-consequence paths boring and central.

Transaction logic was isolated from controllers so balance changes followed one audited path. Mutating requests re-validated ownership server-side to reduce IDOR risk. Session-based tokens made revocation straightforward during live events. MongoDB supported flexible event metadata, although a future version could use PostgreSQL for stronger ledger guarantees.

Next version

Confidence comes from the work still left to do.

I would add integration tests around transaction logic, rate limiting on payment endpoints, and stronger observability before treating the system as production-ready. C-Pay was used for campus events, not commercial payment volume.

03 / Code pattern

Fail closed, check ownership.

A representative middleware pattern used to prevent unauthorized access to wallet and transaction resources.

const verifyOwnership = (Model, paramField = 'id') => {
  return async (req, res, next) => {
    const resource = await Model.findById(req.params[paramField]);

    if (!resource) return res.status(404).json({ error: 'Not found' });
    if (resource.userId.toString() !== req.user.id.toString()) {
      return res.status(403).json({ error: 'Forbidden' });
    }

    req.resource = resource;
    next();
  };
};
